# Техническое задание: безопасный адаптивный тест сетевых дисков DriveGauge

## 1. Назначение

Добавить в DriveGauge отдельный механизм тестирования сетевых томов SMB, NFS, WebDAV и других удалённых файловых систем. Сетевой тест не должен блокировать интерфейс приложения, обязан показывать фактическое движение данных и должен корректно завершаться при зависании сервера, потере соединения, нехватке места или запрете записи.

Локальный алгоритм тестирования встроенных, USB-, Thunderbolt- и других локальных накопителей должен остаться без изменений, кроме общих безопасных улучшений, явно перечисленных в этом документе.

## 2. Проблема текущей реализации

1. `statfs`, чтение resource values и проверка доступности каталога могут обращаться к сетевому серверу синхронно.
2. `startBlockReason` вычисляется SwiftUI несколько раз при отрисовке и сейчас способен вызвать сетевой `statfs` на главном потоке.
3. `pwrite`, `pread`, `fsync`, `open`, `close` и `unlink` на сетевом томе могут ждать ответа сервера неопределённое время.
4. Отмена Swift `Task` не прерывает уже выполняющийся блокирующий системный вызов.
5. Фиксированный файл 1 или 4 ГБ не подходит для медленного соединения: тест может длиться десятки минут.
6. Большая глубина очереди может перегрузить SMB/NFS, сервер или Wi-Fi и сделать весь Mac визуально неотзывчивым.

## 3. Обязательные результаты

После реализации:

- сетевой том определяется автоматически;
- в интерфейсе явно отображается тип `Сетевой` и, если доступно, протокол `SMB`, `NFS`, `WebDAV` или имя файловой системы;
- ни одна потенциально блокирующая операция с сетевым томом не выполняется на `MainActor`;
- нажатия, перемещение окна и кнопка остановки остаются отзывчивыми во время теста;
- сетевой тест работает ограниченное время и адаптирует объём данных к фактической скорости;
- под скоростью показывается точное число подтверждённых записанных или прочитанных байтов;
- неподвижный счётчик сопровождается сообщением о времени без передачи;
- зависший тест автоматически завершается с понятной причиной;
- приложение никогда не удаляет пользовательские файлы и удаляет только созданный им уникальный временный файл;
- незавершённые и ошибочные тесты не записываются в историю как успешные;
- успешный результат сохраняется в существующей SQLite-базе с признаком сетевого профиля;
- сборка остаётся только `arm64` для Apple Silicon.

## 4. Определение типа тома

### 4.1 Основной признак

Использовать `URLResourceValues.volumeIsLocal == false`.

### 4.2 Дополнительный признак

Получать имя файловой системы через `statfs.f_fstypename`. Значения `smbfs`, `nfs`, `webdav` и другие известные удалённые типы считать сетевыми даже при отсутствующем или ошибочном `volumeIsLocal`.

### 4.3 Модель

В `VolumeInfo` добавить тип транспорта/файловой системы, достаточный для:

- выбора локального или сетевого движка;
- отображения протокола;
- сохранения типа теста в истории;
- тестирования логики без реального сетевого подключения.

Не строить решение на имени диска или пути `/Volumes/...`.

## 5. Разделение движков

### 5.1 Локальный движок

Существующий `BenchmarkEngine` продолжает выполнять локальные профили. Он не должен использоваться для сетевого тома.

### 5.2 Сетевой движок

Создать отдельный `NetworkBenchmarkEngine`, который управляет отдельным исполняемым процессом `DriveGaugeNetworkWorker`.

Причина отдельного процесса: зависший сетевой системный вызов нельзя надёжно остановить отменой Swift concurrency. Завершение worker-процесса не должно завершать или блокировать UI DriveGauge.

### 5.3 Worker

Добавить отдельный executable target в `Package.swift`. При сборке worker должен помещаться внутрь приложения, например:

`DriveGauge.app/Contents/Helpers/DriveGaugeNetworkWorker`

Worker не содержит UI и выполняет только один тест за запуск.

## 6. Протокол между приложением и worker

### 6.1 Запуск

Приложение запускает worker через `Process`, передавая аргументы без shell-интерпретации:

- путь выбранного тома;
- идентификатор режима;
- максимальный объём, выбранный пользователем;
- целевую длительность;
- размер блока;
- идентификатор запуска.

Запрещено собирать shell-строку или выполнять путь через `/bin/sh`.

### 6.2 Вывод

Worker пишет в stdout по одной JSON-записи на строку. Минимальные события:

- `ready`;
- `probeStarted`;
- `writing`;
- `syncing`;
- `reading`;
- `completed`;
- `failed`;
- `cleanupCompleted`.

Событие прогресса содержит:

- фазу;
- фактически завершённые байты;
- общий запланированный объём;
- текущую и среднюю скорость;
- время от начала фазы;
- время с последнего подтверждённого блока;
- номер прохода;
- при необходимости системный код ошибки.

stderr сохраняется в диагностический лог, но не показывается пользователю без безопасной нормализации.

### 6.3 Совместимость и ошибки протокола

- Каждое сообщение содержит версию протокола.
- Неизвестные дополнительные поля игнорируются.
- Невалидная JSON-строка не должна обрушать приложение.
- Если worker завершился без `completed`, тест считается ошибочным.

## 7. Алгоритм сетевого теста

### 7.1 Предварительная проверка

В worker:

1. Проверить существование корня тома.
2. Получить доступное место.
3. Проверить требуемый резерв не менее 64 МиБ сверх тестового файла.
4. Создать файл с именем `.drive-gauge-<UUID>.tmp` через `O_CREAT | O_EXCL`.
5. Не использовать маски, поиск или очистку других файлов.
6. Выполнить пробную последовательную запись 4 МиБ блоками по 1 МиБ.
7. Синхронизировать пробу и определить приблизительную скорость.

Если нельзя безопасно определить место, создать файл, записать, синхронизировать или прочитать его, основной тест не начинается.

### 7.2 Адаптивный объём

Основной объём рассчитывается по скорости пробной записи и целевой длительности. Требования:

- стандартная целевая длительность одной основной фазы: 12 секунд;
- минимальный основной объём: 8 МиБ;
- максимальный объём: выбранные пользователем 256 МБ, 1 ГБ или 4 ГБ;
- дополнительно ограничить объём безопасно доступным местом минус резерв;
- округлить объём вниз до целого числа блоков;
- не создавать заранее разреженный файл выбранного максимального размера;
- фактически записывать файл постепенно до адаптивной границы.

На очень медленной сети допускается завершить фазу по времени после полного блока, даже если минимальный объём не достигнут. В результате сохраняется фактически переданный объём.

### 7.3 Стандартный сетевой профиль

- последовательная запись;
- блок 1 МиБ;
- QD1;
- один проход;
- `fsync` измеряется отдельной фазой `syncing`;
- затем файл закрывается и вновь открывается для последовательного чтения;
- чтение выполняется по тому же фактически записанному диапазону;
- итоговая подтверждённая скорость записи включает время финального `fsync`;
- дополнительно можно хранить потоковую скорость до `fsync` для диагностики, но не выдавать её за подтверждённую скорость записи.

### 7.4 Остальные режимы

В первой реализации сетевой движок обязан безопасно поддержать:

- `Стандартный`: QD1, 1 МиБ, 12 секунд;
- `Максимальная скорость`: последовательный профиль с ограниченной очередью не выше QD4 и 12 секунд;
- `Работа приложений`: небольшие блоки 64 КиБ, QD1, не более 8 секунд, без массового создания отдельных файлов;
- `Полный тест`: последовательный запуск трёх сетевых профилей с отдельными результатами и общим жёстким лимитом времени.

Если безопасная реализация какого-либо расширенного профиля не помещается в текущую итерацию, режим должен быть явно недоступен для сетевого тома с объяснением. Запрещено молча запускать локальный алгоритм вместо сетевого.

## 8. Тайм-ауты, зависание и остановка

### 8.1 Наблюдение

Основное приложение отслеживает время последнего события с увеличившимся числом байтов.

- после 3 секунд без новых байтов показать: `Нет передачи данных · 3 с`;
- обновлять счётчик ожидания раз в секунду;
- после 15 секунд без новых байтов считать фазу зависшей;
- для `syncing` использовать отдельный предел 20 секунд;
- общий предел стандартного сетевого теста: 60 секунд;
- полный тест имеет рассчитанный предел, но не более 180 секунд.

### 8.2 Завершение

При ручной остановке или тайм-ауте:

1. Отправить worker `terminate()`.
2. Подождать не более 2 секунд.
3. Если он не завершился, отправить `SIGKILL` только PID запущенного worker.
4. Не использовать `pkill`, маски процессов или завершение по имени.
5. Дождаться завершения обработчиков stdout/stderr.
6. Показать пользователю `Тест остановлен` или конкретную причину тайм-аута.

После аварийного завершения приложение может попытаться удалить только заранее сохранённый точный путь собственного временного файла. Такая очистка также выполняется не на главном потоке и имеет тайм-аут. Неудачная очистка показывается как предупреждение с точным именем оставшегося файла.

## 9. Отзывчивость интерфейса

Запрещены на `MainActor` для сетевого тома:

- `statfs`;
- `resourceValues`;
- `FileManager.isWritableFile`;
- `access`;
- `open`, `read`, `write`, `fsync`, `close`, `unlink`;
- ожидание `Process.waitUntilExit`;
- синхронное чтение Pipe до EOF.

### 9.1 Проверка возможности старта

Заменить вычисляемый `startBlockReason`, выполняющий I/O, на сохранённое состояние:

- `unknown`;
- `checking`;
- `ready`;
- `blocked(reason)`.

Проверка запускается асинхронно после выбора диска или изменения размера. Пока идёт проверка, кнопка отключена и отображает `Проверяем доступ…`.

### 9.2 Обновление списка томов

Сканирование томов выполнять вне `MainActor`. На главный поток передавать только готовый массив `VolumeInfo`.

### 9.3 Частота UI-событий

Worker может сообщать часто, но модель обновляет UI не чаще 10 раз в секунду. Последнее событие фазы и финальное событие доставляются всегда.

## 10. Интерфейс

Для сетевого тома:

- рядом с названием отображается `Сетевой · SMB` или фактический тип;
- вместо неясной подготовки показываются конкретные этапы;
- под скоростью всегда показывается точный счётчик, например `Записано 18 874 368 байт из 134 217 728`;
- при чтении: `Прочитано … байт из …`;
- при синхронизации: `Ожидаем подтверждение сервера`;
- при отсутствии движения: `Нет передачи данных · N с`;
- отображается прошедшее и приблизительное оставшееся время, если его можно оценить;
- кнопка `ОСТАНОВИТЬ` остаётся активной;
- после остановки интерфейс возвращается в стабильное состояние не позднее 3 секунд;
- результат помечается как `Сетевой адаптивный тест`;
- пояснение указывает, что измеряется путь целиком: Mac → сеть → сервер → файловая система/накопитель.

Не называть сетевой результат чистой скоростью физического диска сервера.

## 11. История и SQLite

Успешная запись истории должна дополнительно сохранять:

- локальный или сетевой тип теста;
- протокол/тип файловой системы;
- фактически протестированное количество байтов;
- длительность записи, синхронизации и чтения;
- профиль и глубину очереди;
- признак адаптивного объёма;
- версию алгоритма.

Миграция базы должна быть обратимо-безопасной: существующие записи продолжают читаться, новые поля допускают `NULL` или разумные значения по умолчанию.

Отменённый, зависший или частично выполненный тест в историю успешных тестов не добавляется.

## 12. Безопасность данных

1. Создание только через `O_EXCL` с UUID в имени.
2. Путь временного файла строится только внутри выбранного корня тома.
3. Перед удалением проверяется точное совпадение с путём текущего запуска.
4. Запрещены glob, рекурсивное удаление и перечисление файлов для очистки.
5. Существующий файл никогда не открывается с `O_TRUNC`.
6. При нехватке места тест не начинается.
7. Во время записи ошибка `ENOSPC` немедленно завершает тест и сохраняется как ошибка, а не результат.
8. Логи не должны содержать пользовательские имена файлов, кроме собственного временного файла.

## 13. Диагностика

Добавить ограниченный локальный диагностический журнал сетевого теста:

- идентификатор запуска;
- тип сети/ФС;
- этапы и длительности;
- коды ошибок;
- факт тайм-аута/остановки;
- результат очистки.

Не записывать содержимое тестовых данных. Ограничить размер журнала и не хранить бесконечную историю.

## 14. Тесты

### 14.1 Модульные

- классификация локальных и сетевых типов ФС;
- расчёт адаптивного объёма при медленной, средней и быстрой сети;
- ограничение по свободному месту и выбранному максимуму;
- декодирование всех JSON-событий и неизвестных полей;
- переходы `unknown/checking/ready/blocked`;
- вычисление времени простоя;
- запрет сохранения незавершённого результата;
- безопасная проверка имени временного файла;
- миграция SQLite со старой схемы.

### 14.2 Интеграционные

Запуск worker в локальном временном каталоге в принудительном сетевом режиме:

- успешная запись/чтение малого объёма;
- корректные монотонно растущие счётчики байтов;
- удаление только своего файла;
- отказ при каталоге без записи;
- отказ при недостаточном месте через внедряемый тестовый лимит;
- остановка worker;
- принудительное зависание тестовым флагом и срабатывание watchdog;
- повреждённая JSON-строка;
- аварийный exit worker.

### 14.3 Сборка и статические проверки

- `swift build -c release`;
- smoke-тест существующего локального движка;
- интеграционные тесты worker;
- `codesign --verify --deep --strict`;
- `lipo -archs` возвращает только `arm64`;
- `hdiutil verify` для DMG;
- `git diff --check`.

### 14.4 Ручная приёмка

На доступном сетевом томе с небольшим безопасным лимитом:

- выбрать том;
- дождаться асинхронной проверки;
- начать стандартный тест;
- двигать окно и переключать доступные элементы;
- наблюдать рост точного счётчика байтов;
- остановить тест и подтвердить возврат UI не позднее 3 секунд;
- повторить успешный тест;
- убедиться в появлении результата в истории;
- отключить сеть/сервер и проверить сообщение о простое и тайм-аут;
- убедиться, что пользовательские файлы не изменены.

Ручная проверка на реальном сервере не заменяет автоматические тесты, а автоматические тесты не считаются доказательством поведения конкретного SMB/NFS-сервера.

## 15. Критерии приёмки

Работа считается выполненной только если одновременно выполнены все пункты:

1. Сетевой том автоматически выбирает отдельный движок.
2. На главном потоке не осталось синхронных сетевых проверок.
3. Worker включён в `.app` и запускается без shell.
4. Стандартный адаптивный профиль работает и ограничен по времени.
5. Точный счётчик подтверждённых байтов растёт во время передачи.
6. Watchdog показывает простой и завершает зависший worker.
7. Ручная остановка возвращает интерфейс за установленное время.
8. Временный файл создаётся и удаляется безопасно.
9. Ошибочный/отменённый тест не попадает в историю успешных.
10. История хранит сетевые метаданные, старые записи читаются.
11. Все обязательные автоматические тесты проходят.
12. Приложение собрано и подписано только для Apple Silicon.
13. Независимый проверяющий не обнаружил несоответствий ТЗ уровня blocker/critical.
14. Независимый ревьюер не обнаружил ошибок безопасности данных или блокировки UI.

## 16. Порядок командной работы

1. Разработчик реализует решение и собственные тесты строго по этому ТЗ.
2. Проверяющий ТЗ составляет матрицу `требование → код → тест → статус` и фиксирует пропуски.
3. Независимый ревьюер анализирует корректность, конкурентность, тайм-ауты, безопасность удаления и миграцию базы.
4. Все найденные blocker/critical/major возвращаются разработчику.
5. После исправлений оба проверяющих выполняют повторную проверку.
6. Главный агент самостоятельно запускает сборку, тесты и проверяет итоговый diff.
7. Версия, appcast, коммит, тег и GitHub Release создаются только после прохождения критериев приёмки.

## 17. Ограничения текущей итерации

- Не измерять SMART через сетевой том: это задача сервера, а не клиента SMB/NFS.
- Не устанавливать сторонние приложения или `fio` пользователю.
- Не менять результаты и алгоритм локального теста без необходимости.
- Не публиковать релиз при отсутствии доказательства безопасной остановки worker и удаления только собственного временного файла.
